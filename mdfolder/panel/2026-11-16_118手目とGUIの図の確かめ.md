### 問い 1：なぜ一致しないのか、学習が足りないのか

**結論**：不一致の理由は、GUI の「モデルの手」が探索をしない policy の 1 位であり、policy が「floodgate の棋譜で指された手の確率」を学習した出力だからである。1 局面の不一致からは、学習の量は判断できない。

**一致しない理由（6 つ）**

1. 2 つの手の定義が違う。GUI の「モデルの手」は、合法手の中で policy の値が最大の手である（xai_app.py:832-836）。GUI は「モデルの手」を決めるときに value と探索を使わない（xai_app.py:839 の記録は "Model's move (legal, highest policy)"）。
2. policy の学習の目標は、棋譜で指された手だけである。棋譜に P の欄がないとき、学習の目標は指された手に 1 を置く分布になる（minizero/minizero/environment/base/base_env.h:252-258）。data/floodgate/sgf_2250/test.sgf の 1 局目の先頭の 400 文字には、P の欄がなかった（ホストで head -c 400 を実行した）。train.py:257-273 の 2 つの式（KL ダイバージェンスと交差エントロピー）は、学習の目標が 1 つの手に 1 を置く分布のとき同じ値になる。2 つの式のどちらにも、詰みまでの手数を比べる項はない。SL の学習に使われた設定ファイルの名前は、確かめていない。
3. まとめ役が計算した 4 つのモデルのどれでも、policy の 1 位は ▲4七桂打 ではなかった（「118 手目までの局面の計算」）。合法手の中で割り直した policy は次のとおりである。
   - SL の 10T：▲5六銀打 0.582、▲6六銀打 0.204、▲5六金打 0.102、▲6六金打 0.074、▲5六香打 0.023、▲4七桂打 0.005（6 位）。
   - SL の R3(RRT)：▲5六銀打 0.426、▲5六香打 0.185、▲6六銀打 0.159、▲4七桂打 0.088（4 位）。
   - SL の 10T から始めた RL の 10T（models/9x9_shogi/eval/10T_fg/weight_iter_250000.pt）：▲6六銀打 0.252、▲6六金打 0.240、▲5六香打 0.207、▲4七桂打 0.033（7 位）。
   - 論文の自己対局の R3(RRT)：▲5六銀打 0.237、▲6六銀打 0.168、▲4七桂打 0.093（3 位）。
4. SL のモデルの統計では、policy の 1 位が指された手と違う局面のほうが多い。floodgate の test の 39,654 局面で、policy の 1 位が指された手である割合は、SL の 10T が 0.474、SL の R3(RRT) が 0.504 である（models/9x9_shogi/sl_check/test_positions.txt:2, 6）。101 手目以降の 10,909 局面では、割合は 0.410 と 0.445 である（test_positions.txt:4, 8）。指された手が policy の 5 位以内に入る割合は 0.842 と 0.866 である（test_positions.txt:2, 6）。SL の 10T の ▲4七桂打 は 6 位なので、118 手目までの局面は、SL の 10T の統計では「5 位以内に入らない 15.8% の局面」と同じ種類である。合法手から無作為に 1 手を選ぶときの一致の割合は、確かめていない。test は floodgate のコンピュータ同士の棋譜であり、人間の棋譜での一致の割合は測られていない。
5. 指導教員の役が再実行した水匠5（500 万ノード、MultiPV 5）は、▲4七桂打 に 5 手の詰み、▲5六銀打 と ▲6六銀打 に 13 手の詰み、▲5六香打 に 15 手の詰みを示した。水匠5 の出力が正しければ、SL の 10T の policy の上位 2 手は、どちらも詰みの手である。2 つの手の違いは、水匠5 が示した詰みの手数の違いである。まとめ役は水匠5 を実行していない。
6. 同じネットワークの value の出力は、▲4七桂打 を最も高く評価する。まとめ役は、250 の合法手の各手のあとの局面を入力にして value を計算し、先手から見た値に直した（value は手番側から見た値である。scripts/sl_model_check.py:120）。SL の 10T では ▲4七桂打 +0.364 が 1 位で、▲5六銀打 は +0.070 の 4 位だった。SL の R3(RRT) では ▲4七桂打 +0.706 が 1 位で、▲5六銀打 は +0.387 の 3 位だった。SL の 10T から始めた RL の 10T でも ▲4七桂打 +0.570 が 1 位だった。論文の自己対局の R3(RRT) では、▲4七桂打 は +0.255 の 10 位で、1 位は ▲6六銀打 +0.432 だった。

**探索ありで ▲4七桂打 が選ばれる仕組み（コードで確かめた範囲）**

- Gumbel の探索は、根の合法手を policy_logit の大きい順に 16 手に絞る（minizero/minizero/actor/gumbel_zero.cpp:96-97、configs/9x9_shogi/10T-bigserver.cfg:45）。▲4七桂打 は SL の 10T で 6 位、SL の R3(RRT) で 4 位なので、Gumbel のノイズがなければ 16 手に入る。
- 最後の手は、訪問回数が最大の手ではない。最後の手は、policy_logit +（50 + 最大の訪問回数）× 正規化した Q が最大の手である（gumbel_zero.cpp:60-65, 121-136、zero_actor.cpp:189-190、10T-bigserver.cfg:46-47）。
- したがって、アシスタントの記録の「訪問回数で選ぶ」は、コードと合わない。分野の教授の役の指摘は正しい。
- アシスタントの記録の「ノイズなし」は、確かめていない。scripts/usi_bridge.py:257-260 の既定の conf_str は Dirichlet のノイズを切るが、actor_use_gumbel_noise=true（10T-bigserver.cfg:44）は切らない。アシスタントが渡した conf_str は、まとめ役には見えない。
- 探索あり（64 シミュレーションと 800 シミュレーション）で ▲4七桂打 が指されたという記録は、まとめ役は再実行していない。探索の木の Q と訪問回数も、確かめていない。

**学習が足りないか**

- 「学習が足りない」には 3 つの意味がある（分野の教授の役の整理）。1 つ目は「損失が下がりきっていない」、2 つ目は「118 手目までの局面の policy の 1 位が変わる」、3 つ目は「policy と value が同じ手を選ばない」である。
- 1 つ目の意味では、学習曲線が答える。SL の 10T の test の policy の損失は 1.7910 から 1.7291 に下がり、test の正解率は 0.4723 から 0.4831 に上がった（models/9x9_shogi/sl_check/curves.txt:3, 12）。SL の R3(RRT) は 1.6250 から 1.5906、0.5025 から 0.5092 である（curves.txt:15, 24）。学習率は最後まで 0.02 である（curves.txt:1, 13）。
- 2 つ目の意味では、証拠がない。SL の 10T より 100,000 ステップ多く学習した RL の 10T でも、policy の 1 位は ▲6六銀打 で、▲4七桂打 は 7 位だった。ただし、RL の学習の目標は、自己対局の棋譜の P の欄の分布であり（minizero/minizero/environment/base/base_env.h:259-266）、floodgate の棋譜で指された手ではない。RL の 10T は、SL を長く学習したモデルの代わりにはならない。SL の途中の重みでの比較は、行われていない。
- SL の 10T から始めた RL の 10T の 31 勝 9 敗（models/9x9_shogi/sl_check/SL_10T_vs_RLfromSL_10T.txt の最後の 5 行、W-D-L = 9-0-31）は、学習の方法、100,000 ステップの追加、学習率の 3 つが同時に違う（mdfolder/after_gpw_submission.md:208）。まとめ役が計算し直した両側の二項検定の p は 0.00068、Wilson の 95% 信頼区間は 0.62〜0.88 である。31 勝 9 敗から言える文は「SL の 10T より強い 10T がある」までである。
- mdfolder/after_gpw_submission.md の 5.5 節の 1.744 と 5.6 節の 1.729 は、どちらも正しい。1.744 は 150,000 ステップ目の 1 回の記録である（models/9x9_shogi/fg_10T_pretrain.log:10500-10504）。1.729 は 145,001〜150,000 ステップの平均である（curves.txt:12）。

**SL のモデルの統計は行われたか（本人の問い）**

行われた統計は 4 種類である。まとめ役は、結果のファイルを読んだ。まとめ役は、39,654 局面の計算をやり直していない。

1. policy の 1 位が指された手である割合、指された手が 5 位以内である割合、手数の区間ごとの割合、value の符号が勝敗と合う割合（models/9x9_shogi/sl_check/test_positions.txt:1-8）。
2. 学習曲線（models/9x9_shogi/sl_check/curves.txt）。
3. 対局の勝敗（models/9x9_shogi/sl_check/ の 7 つの txt。まとめ役が読んだファイルは SL_10T_vs_RLfromSL_10T.txt だけである）。
4. Attention の集計が 2 つ。11-05 の「指された手と他の手」（gpw_paper/poster_parts.md:186-204。0.5 が偶然の値）と、11-16 の「重みが最大のマスがモデルの手の行き先である割合」（data/floodgate/examples_sl.csv）。

行われていない統計は 6 つである。

1. 駒打ちの打つ先を起点にした重みの集計（118 手目までの局面の図と同じ量）。
2. 起点を替えたベースラインと、「直前の相手の手の行き先」との比較。査読者の役の 577 局面とまとめ役の 1,024 局面の小さな試しだけがある。
3. 信頼区間。同じ棋譜から複数の局面を取るので、棋譜を単位にした再標本化が要る。
4. 人間の棋譜での一致の割合。
5. 水匠5 が詰みを示す局面で、policy の 1 位が詰みの手である割合。
6. 探索ありの手が指された手と一致する割合。

4 番から 6 番の統計がリポジトリのどこにもないことは、確かめていない。

**118 手目までの局面の図（52 枚）で、読む人が誤って読む点（8 つ）**

1. 凡例の「SL の 10T の手 ▲5六銀打」（xai_app.py:838）は、探索をしない policy の 1 位である。図には「探索なし」と書かれていない。読む人は「SL の 10T は対局で ▲5六銀打 を指す」と読む。
2. 名前の「118手目」（tsume_shogi.py:364、フォルダ名）は、手の番号と合わない。棋譜は 119 手で、118 手目は後手の 5d5e、119 手目が ▲4七桂打 である（「118 手目までの局面の計算」）。論文は「118 手目までの局面（次の 119 手目に ▲4七桂打）」と書いている（gpw_paper/paper.tex:451）。floodgate の例の図は「160手目まで」と書いている。

### 分野の教授（Opus 5.5）

#### 問い 1

結論：GUI の「モデルの手」と実際に指された手が一致しないのは、GUI の「モデルの手」が探索をしない policy の 1 位であり、同じネットワークの value の出力は ▲4七桂打 を最も高く評価しているからである。118 手目の 1 局面だけでは「学習が足りない」とは結論できない。

1. GUI の「モデルの手」の定義：xai_app.py:832-836 は、合法手（legal_moves）の中で policy の値が最大の手を選ぶ（top = max(legal, key=lambda m: float(pol[usi_to_action_id(m, is_black)]))）。value も探索も使わない（xai_app.py:839 のログも "Model's move (legal, highest policy)"）。

2. policy と value の不一致（私が CPU で測った値）：合法手は 250 手。SL の 10T の policy（合法手で割り直した値）は ▲5六銀打 0.582、▲6六銀打 0.204、▲5六金打 0.102、▲4七桂打 0.005 で、▲4七桂打 は policy_logit の順位で 6 位。SL の R3(RRT) は ▲5六銀打 0.426、▲5六香打 0.185、▲6六銀打 0.159、▲4七桂打 0.088（4 位）。どちらもアシスタントの数値と一致した。一方で、各合法手を指したあとの局面の value を手番が後手なので符号を反転して先手から見た値（scripts/sl_model_check.py:120 で value は手番側から見た値）は、SL の 10T で ▲4七桂打 +0.364 が 250 手の中で 1 位、▲5六銀打 は +0.070。SL の R3(RRT) でも ▲4七桂打 +0.706 が 1 位、▲5六銀打 は +0.387。同じネットワークで、policy の出力は ▲5六銀打 を 1 位にし、1 手先の value の出力は ▲4七桂打 を 1 位にする。なお SL の 10T の根の value は -0.182 で、先手が詰ませられる局面を先手のやや不利と評価している。

3. 探索が ▲4七桂打 を選ぶ仕組み（コードで確かめた）：minizero/minizero/actor/gumbel_zero.cpp:96-97 は根の合法手を policy_logit の大きい順に actor_gumbel_sample_size=16 手（configs/9x9_shogi/10T-bigserver.cfg:45）に絞る。▲4七桂打 は SL の 10T で 6 位、SL の R3(RRT) で 4 位なので候補の 16 手に入り、Gumbel のノイズを加えても候補に入る確率は 0.998 と 1.000（私の 20,000 回のサンプル）。最後の手は訪問回数の最大ではなく、gumbel_zero.cpp:62-65 が sortCandidatesByScore を呼び、gumbel_zero.cpp:130 の score = policy_logit + (actor_gumbel_sigma_visit_c + 最大の訪問回数) × actor_gumbel_sigma_scale_c × Q（c_visit=50、c_scale=1、10T-bigserver.cfg:46-47）が最大の手になる。Q の差には 51 以上が掛かるので、SL の 10T で 1 回ずつ訪れた時点の Q の差 0.294（+0.364 − +0.070）は score で 15 以上になり、policy_logit の差 ln(0.582/0.005) ≈ 4.76 を上回る。したがって 64 シミュレーションでも ▲4七桂打 が選ばれたことは、value の出力で説明できる。実際の探索の木の Q と訪問回数は確かめていない。
