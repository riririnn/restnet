# カリキュラムトレーニング設計案（2026-07-07 改訂）

## 改訂の背景：引き分けの悪循環（実測データで確認済み）

iter 38 までの学習データ分析で、以下の**悪循環**が定量的に確認された。

| 指標 | iter 1 | iter 38 | 傾向 |
|------|--------|---------|------|
| 引き分け率 | 9.7% | **64.6%** | 単調増加 |
| 平均ゲーム長 | 278手 | **428手**（中央値498手） | 単調増加 |
| ValueLoss | 0.86 | **0.30で停滞** | 「常に0と予測」の理論値0.35に漸近 |

### 悪循環の構造

```
モデルが詰ませられない
  → ゲームが500手上限まで続く（68%が495手以上）
  → 引き分け率が上昇（価値ターゲットの65%が0）
  → 価値ネットが「常に互角」と学習（ValueLoss 0.30 ≈ 全部0と予測）
  → resign_threshold=-0.9 が発動しない
  → ゲームがさらに長引く → 最初に戻る
```

### 時間への影響

- 1 iter の総手数: 囲碁 9x9 の約4〜8倍（1000局×428手 = 42.8万手）
- **学習が遅い主因は実装の遅さではなく「ゲームが終わらない」こと**
- 手/秒の処理速度は囲碁比 約2倍差で妥当（入力362ch・行動空間5000超を考慮）

### この結論に至った根拠（4つの独立した証拠）

単一指標の偶然ではなく、別々のデータソースが同じ構造を指していることで確定した。

1. **引き分け率**（SGFの `RE[]` タグを集計）
   - `sgf/*.sgf` の各ゲームの `RE[...]` を正規表現 `RE\[([^\]]+)\]` で抽出。
     `"0"`/`"0.000000"` を引き分けとして数えると 9.7%→64.6% の単調増加。
2. **引き分けの報酬が0であること**（C++コードを直接確認）
   - [shogi.cpp:206-208](../minizero/minizero/environment/shogi/shogi.cpp#L206-L208)
     `getEvalScore()`: `BLACK_WON→+1`, `WHITE_WON→-1`, **それ以外（DRAW含む）→0**。
   - [shogi.cpp:118](../minizero/minizero/environment/shogi/shogi.cpp#L118)
     500手到達時に27点法で判定し、同点なら `GameResult::DRAW`（報酬0）。
3. **手数分布**（SGFの指し手数を集計）
   - `38.sgf`（1000局）は中央値498手、**68.3%が495手以上**。
     「詰ませられず500手上限→引き分け」の流れを裏付ける。
4. **ValueLossの停滞**（学習ログ `op.log`）
   - `loss_value` が 0.86→0.30 で停滞。価値ネットが「常に0（互角）と予測」する
     戦略のMSE損失は報酬の分散に一致し、引き分け6割のデータではこれが約0.3。
     実測値と一致するため「価値ネットが引き分けに引きずられている」と確定。

## MiniZero / AlphaZero はこの問題をどう回避しているか

引き分けの多発は**将棋・チェス特有**の問題で、囲碁では原理的に起きない。
元のフレームワークが将棋でこの問題に「対処していた」のではなく、
**評価していたゲーム（囲碁・Hex）では問題が発生しなかった**というのが実態。

### 囲碁：komi 7.5（半整数）で引き分けが原理的に消える

- [go.cpp:104](../minizero/minizero/environment/go/go.cpp#L104) `komi_ = env_go_komi`、
  [configuration.cpp:78](../minizero/minizero/config/configuration.cpp#L78) `env_go_komi = 7.5`。
- [go.cpp:259-275](../minizero/minizero/environment/go/go.cpp#L259-L275) `getEvalScore()` は
  地の差で勝者を決めるが、**komiが7.5（半整数）なので地の差が整数±0.5となり、
  絶対に同点にならない**。よって囲碁は実質的に引き分け0。
- Hexも構造上引き分けが存在しないゲーム。
- → 元論文が扱った2ゲームは、そもそも「引き分けの悪循環」が発生しえない。

### AlphaZero（DeepMind）のチェス・将棋での対処

DeepMindの将棋・チェスは引き分けが起きうるが、以下で顕在化を防いでいた：

- **十分に強いネットワーク + 大量の探索**（TPU数千個、800 simulations/手）。
  モデルが早期に「勝ち切る力」を持つため、引き分け地獄に陥る前に棋力が立ち上がる。
- **Resignation（投了）** で敗勢のゲームを早期終了し、無駄な長手数を削減。
- **引き分けは価値0のターゲット**として素直に扱う（対処というより許容）。
- 我々の環境（RTX 5060 Ti 1枚、64 simulations/手）は探索・計算資源が桁違いに小さく、
  モデルが「勝ち切る力」を獲得する前に引き分けデータで飽和してしまう。
  = **同じ設計でも資源が小さいと悪循環に入りやすい**。

### まとめ

| ゲーム | 引き分け | 理由 |
|--------|---------|------|
| 囲碁（元論文） | 実質0 | komi 7.5 で地の差が非整数 |
| Hex（元論文） | 0 | ルール上引き分けが存在しない |
| チェス・将棋（AlphaZero） | 起きるが許容 | 強力なネット+探索で早期に棋力が立つ |
| **本研究の将棋** | **64.6%** | **小資源でモデルが弱く、500手上限→引き分けに飽和** |

→ 我々は「引き分けが起きないゲーム」を前提に作られた設計を、
引き分けが起きる将棋に小資源で適用したため、独自の対処が必要になった。

## 我々が実際に行った対処（2026-07-07 時点）

### 完了済み（実装・計測の詳細）

#### 1. 問題の定量診断

`sgf/*.sgf` と `op.log` をPythonで集計。手順は上記「4つの独立した証拠」を参照。
コードは書き捨てのワンライナー（`re.finditer(r"\(;GM\[")` でゲーム分割 →
各ゲームの `RE[]`・指し手数を集計）。iter 1〜38 を横断して傾向を確認した。

#### 2. ELO測定パイプライン（`scripts/shogi_eval.py`）

**動機**: 標準の対戦ツール `gogui-twogtp` が将棋で使えなかった。
[shogi.h:44-46](../minizero/minizero/environment/shogi/shogi.h#L44-L46) の
`ShogiAction::toConsoleString()` が空文字を返すスタブのため、`genmove` の応答が
空になり、審判ツールが指し手を取得できず0手で終局扱いになる。

**実装方法**（C++リビルド不要の回避策）:
- 2つの `restnet_shogi` プロセスを別モデルで起動（`Engine` クラス）。
  各エンジンに `-conf_str "nn_file_name=<model>.pt"` で別々の重みを渡す。
- コンソール（GTP風）を `subprocess.Popen` で駆動。起動時に設定値が大量出力
  されるため、`send()` は行頭が `=`（成功）/ `?`（失敗）の framed reply を
  スキャンして応答を切り出す。
- **指し手の取得**: `genmove` の応答が空なので、代わりに `game_string`
  コマンドで棋譜全体を取得し、`;[BW]\[(\d+)\]` の**最後の行動ID**を読む
  （`last_action_id()`）。それを相手エンジンに `play <color> <action_id>` で伝達。
- 終局は `genmove` が `PASS`/`Resign` を返すか手数上限で検知し、
  `final_score`（先手視点の±1/0）で勝敗判定。
- 手番は1局ごとに先後入れ替え（`m1_is_black = (g % 2 == 0)`）、
  先手・後手の有利差を相殺。

**計測方法**:
- 各ペア20局対戦。引き分けは0.5勝として集計。
- ELO差は標準式 `400 * log10(p / (1-p))`（`p` = スコア率）で算出。
- 実行はコンテナ `restnet_eval` 内でバックグラウンド実行し、
  結果を `self_eval/*.txt` に保存。

**結果**:
| 対戦 | スコア | 勝率 | ELO差 |
|------|--------|------|-------|
| iter 5 (weight_1000) vs iter 39 (weight_13000) | 1.0/20 | 5% | **-512** |
| iter 22 (weight_7000) vs iter 39 (weight_13000) | 3.5/20 | 17.5% | **-269** |

→ 学習は機能しており、後半でも約270 ELO伸びている（停滞ではなく減速）。
「実装バグで強くなれない」という最悪シナリオを否定できた。

#### 3. 終盤局面プールの抽出（`scripts/extract_endgame_positions.py`）

**目的**: カリキュラム学習で「短手数で勝敗が付く終盤」から自己対局を
始めるための開始局面プールを作る。

**実装方法**:
- `sgf/*.sgf` から**決着済みゲームのみ**を選ぶ（`RE[]` が引き分け `0` の
  ゲームは価値シグナルにならないので除外）。
- 各ゲームの行動ID列を、C++の `env_py` モジュール（`build/shogi/env_py*.so`）で
  1手ずつ再生（`env.act(env_py.Action(action_id, player))`）。
- 終局の `--offsets`（2,4,6,8）手前の局面で `env.get_features()` を取得し、
  362チャンネルのテンソルを得る。
- **テンソル → SFEN 逆変換**（`features_to_sfen`）: 盤面チャンネル0-27・
  持ち駒チャンネル31-44・手番チャンネル360を読み、SFEN文字列を組み立てる。
  手番が後手のときは盤が反転している点を戻す。
- **検証**: 生成したSFENを `tsume_shogi.sfen_to_tensor()` で逆にテンソル化し、
  元の盤面・持ち駒プレーンと一致するか確認（`validate_sfen`）。
  一致しないものは破棄。

**計測・結果**:
- iter 30〜38 の9ファイルを処理。決着済み750ゲームから **3000局面を抽出**、
  **検証失敗0件**（往復変換が完全一致）。
- 出力: `endgame_pool.sfen`（1行1局面のSFEN）。

### 手数上限の短縮 + 引き分け廃止（2026-07-07 実装・検証済み）

**実装した2つの設定パラメータ**（C++、リビルド済み）:

- `env_shogi_max_moves`（デフォルト500、0で上限撤廃）
  — 27点法判定までの手数上限を可変化。後で上限を撤廃するときも
  リビルド不要で `-conf_str env_shogi_max_moves=0` で切り替えられる。
- `env_shogi_adjudication_no_draw`（デフォルトfalse）
  — 27点法が同点のとき後手勝ちにして引き分けを消す。囲碁のkomi 7.5と同じ発想。

**編集したファイル**:
- [configuration.h](../minizero/minizero/config/configuration.h) — 変数宣言
- [configuration.cpp](../minizero/minizero/config/configuration.cpp) — 既定値と
  `#elif SHOGI` ブロックでのパラメータ登録
- [shogi.cpp:118付近](../minizero/minizero/environment/shogi/shogi.cpp#L118) —
  上限を `config::env_shogi_max_moves` 参照に変更（0で無効化）、
  27点法の同点分岐を `no_draw` フラグで後手勝ちに切り替え
- [configs/9x9_shogi/RRTRRT.cfg](../configs/9x9_shogi/RRTRRT.cfg) —
  `env_shogi_max_moves=200` / `env_shogi_adjudication_no_draw=true` を追記

**検証結果**（同一モデル weight_13000 同士6局、`max_moves=200:no_draw=true`）:
- **引き分け0**（従来64.6%）。全局で勝敗が決定。
- 200手到達局も27点法で勝敗がつく（引き分けにならない）。
- 平均手数 約180手（従来428手）、1局約30秒（従来89秒 = 約1/3）。
- 同一モデル同士の勝率ちょうど50%で先後バランスも健全。

**運用方針**: まず `max_moves=200:no_draw=true` で学習し、棋力が上がって
自力で決着をつけられるようになったら段階的に上限を戻し（200→300→500）、
最終的に `env_shogi_max_moves=0`（撤廃）へ移行する。

### 追加発見（2026-07-07、sgf_stats.sh による再集計）

終局理由を「詰み・投了 / 千日手 / 判定（上限到達）」に3分類した結果、
**引き分けの主因は27点法の同点ではなく千日手**だと判明した。

| iter | 詰み・投了 | 千日手 | 判定到達 | 引分計 |
|------|-----------|--------|---------|--------|
| 1  | 84.1% | 8.9%  | 7.0%  | 9.7%  |
| 20 | 39.7% | 42.3% | 18.0% | 46.5% |
| 38 | 23.7% | **59.9%** | 16.4% | 64.6% |

- 弱いモデル同士が終盤で手を進められず、上限500手の直前（495〜499手）で
  同一局面を繰り返して千日手になるのが引き分けの大半。
- **上限200が効く理由**: 千日手ループに入る前に27点法判定で決着させるから。
  実測（同一モデル10局、`max_moves=200`のみ、no_drawフラグ**なし**）で引き分け0。
- よって `env_shogi_adjudication_no_draw` は不要（デフォルトfalseのまま運用）。
  C++の必須変更は `env_shogi_max_moves` の可変化のみ。

### 採用したカリキュラム（シンプル版・C++追加変更なし）

基礎構造の変更を最小化する方針により、開始局面プール（要C++大改造）は保留し、
**手数上限そのものをカリキュラム軸**とする。切替は `-conf_str` のみ。

| フェーズ | iter | `env_shogi_max_moves` | 狙い |
|---------|------|----------------------|------|
| A | 1〜50 | 200 | 決着を強制、駒得の価値を高速学習 |
| B | 51〜150 | 300 | より長い攻防を許容 |
| C | 151〜300 | 500 | 通常将棋へ移行 |
| 以降 | 手動 | 0（撤廃） | 詰み終局率が十分高くなったら |

併せて `actor_mcts_reward_discount=0.99` を設定（cfg済み）。
50手での詰み勝ち（0.99⁵⁰≈0.61）は200手の判定勝ち（0.99²⁰⁰≈0.13）より
約4.5倍高評価となり、**「駒数勝ち逃げ」ではなく「早い詰み」への学習圧力**になる
（「上限内では詰みを学ばないのでは」という懸念への対策）。

**実行方法**（コンテナ内・/workspace から）:

```bash
./scripts/curriculum_train.sh shogi_9x9_curriculum_n64 0
```

**モニタリング**（終局理由の推移を確認）:

```bash
./scripts/sgf_stats.sh shogi_9x9_curriculum_n64          # 全iter
./scripts/sgf_stats.sh shogi_9x9_curriculum_n64 10 20 30  # 指定iter
```

- 「詰み・投了」の割合が上がっていれば健全（Phase移行の判断材料）
- 「判定」が高止まりしたら駒数戦略に固まっている兆候 → 割引率強化や上限調整を検討

## 対策の全体像（優先度順）

### ★★★ 対策1: 500手上限の短縮（1行変更・即効）

`minizero/minizero/environment/shogi/shogi.cpp` L118 の手数上限を 500→200 に変更。
既実装の27点法判定が早期に発動し、引き分けの大半が勝敗に変わる。

```cpp
// 変更前
if (actions_.size() >= 500 && winner_ == GameResult::UNDECIDED) {
// 変更後
if (actions_.size() >= 200 && winner_ == GameResult::UNDECIDED) {
```

**効果**: SP時間 約2倍短縮 + 価値シグナル（±1）の大幅増加。
**コスト**: C++リビルドのみ。学習は Continue 可能（ただしリプレイバッファの
旧データと混ざるため、新規学習開始を推奨）。

**注意**: 27点法は駒得側が勝ちになるため、序盤モデルには「駒得＝勝ち」という
バイアスがつく。これは将棋の基本原理と整合するので序盤学習にはむしろ好都合。
学習が進んだら上限を 300→500 と戻していく（これ自体がカリキュラム）。

### ★★★ 対策2: 終盤局面からの自己対局開始（本命・要実装）

**現状の制約**: `ShogiEnv::reset()` は常に平手初期配置
（`board_.init(Board::Handicap::Even)`）。開始局面指定の仕組みは存在しない。

**必要な実装**（C++、リビルド必要）:

1. **SFENパーサ**を `board.h/cpp` に追加（`Board::initFromSfen(const std::string&)`）
2. **設定キー追加**: `env_shogi_opening_sfen_file=<path>`（SFENを1行1局面で列挙）
3. **`ShogiEnv::reset()` 改造**: プールが指定されていれば確率的にランダムな
   SFEN局面から開始（`env_shogi_opening_ratio=0.5` のような混合比も設定可能に）

```cpp
void ShogiEnv::reset() {
    if (!opening_pool_.empty() &&
        utils::Random::randReal() < config::env_shogi_opening_ratio) {
        board_.initFromSfen(opening_pool_[utils::Random::randInt() % opening_pool_.size()]);
    } else {
        board_.init(Board::Handicap::Even);
    }
    // ... 以下既存処理
}
```

**局面プールの作り方**（Python、実装容易）:

- 既存の自己対局SGF（38 iter分・数万局）から**決着がついたゲーム**の
  終盤局面（詰みのN手前）を抽出 → 数千局面のプールが即座に作れる
- `tsume_shogi.py` の詰将棋プリセットも加える
- 抽出スクリプト: SGFの行動ID列を `env_py` で再生し、終局M手前の局面を
  SFEN出力（`build/shogi/env_py.so` で可能）
