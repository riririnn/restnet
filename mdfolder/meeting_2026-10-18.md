## 1. 動物将棋：完全解析の全局面での一致率

### 方法

| 項目 | 内容 |
|---|---|
| 局面 | 完全解析の全局面（246,803,167）を、先手番の向き（データの向き）と後手番の向き（180度回して先後を入れ替えた局面）でそれぞれ判定する（モデルは手番で入力が変わるため。下を参照） |
| 判定 | 探索なしで、方策が最大の合法手 |
| 指標 | 最善手を選んだ割合：選んだ手が完全解析の最善手（勝ちなら最短で勝つ手、負けなら最も長く粘る手）である局面の割合。GUI と同じ定義 |
| モデル | 11構成の最終モデル（200 iteration） |

### 完全解析のデータについて確かめたこと

- 田中先生の GitHub：「初期局面から（相手のライオンを取れる時は必ず取るという条件で）到達可能な局面すべてを求め」た。
- 1つのデータは、元の局面・左右反転・180度回して先後を入れ替えた局面・その左右反転をまとめたもの（`dobutsu.h` の `normalize()`：「黒番に正規化した上で64ビット整数に変換し，flipしたものと小さい方を返す」）。左右対称の局面は1万局面中2つだけ。
- 手数0の勝ちは相手のライオンを取れる局面、手数0の負けは相手のライオンがトライ済みの局面（`makeWinLose.cc`）。

- 同じ局面でも向きで結果が変わる。後手番の向きは、勝ちの局面で 0.02〜0.08 高く、負けの局面で 0〜0.05 低い（理由は未確認）。

- GUI（最善手順の近くの局面）では R の多い構成が上だったが、全局面では 6T が上。全局面の57%は相手のライオンを取れる局面で、GUI の局面とは集合がまったく違う。

**向きで結果が変わる理由として確かめたこと**

- 完全解析のデータは、すべて先手番の向きで保存されている（先頭20万局面で確認）。田中先生は後手番の局面を回して先手番と同じ局面として扱う（dobutsu.h の normalize()）。
- 動物将棋の入力は後手番で盤を回さず、手番の印（16・17チャンネル）を持つ（dobutsu.cpp:228〜266）。同じ局面でも、先手番と後手番では盤全体が上下逆の入力になる。
- 9×9 の将棋とミニ将棋は後手番で盤を回す。AlphaZero と中屋敷・金子（GPW 2019）の動物将棋も回す。手番の印は MiniZero のどのゲームにもある。
- 盤を回して学習し直す案は、時間がないので見送った。

## 2. 9×9：外部エンジンとの対局

### 方法：出村・金子（GPW 2023）と同じ

[将棋81万（IPSJ 229354）](https://ipsj.ixsq.nii.ac.jp/records/229354) の 4.3 節を原文で確認した。

| 項目 | 出村・金子 | 本研究 |
|---|---|---|
| 相手 | 水匠5、1手1000ノード、置換表16MB、並列探索・定跡なし | 同じ（1000から下げても測った） |
| 開始局面 | 人間の棋譜集（shogi_depot）の9戦型、20〜40手目からランダム | 同じ棋譜集から作った（`scripts/make_openings.py`、各戦型2000局面、すべて合法手で確認） |
| 先後 | 記載なし | 各局面で先後を入れ替えて2局 |
| こちら | Gumbel、1手16シミュレーション | 16 と 64。ノイズなし、sequential halving で残った手 |
| 局数 | 各戦型2000局 | 試しは各条件90局 |
| 学習量 | 自己対局1000万局（Base は +214 Elo） | 100万局（ResTNet と同じ） |

論文の内容（原文で確認）：

- 目的：将棋の初期局面は1通りなので、AlphaZero 型の自己対局では序盤が似通う。駒の初期配置を入れ替えた 816,480 通りの初期局面（将棋81万）で学習し、いろいろな戦型に強くなるかを調べた。
- 学習：Gumbel AlphaZero、自己対局のみ（人間の棋譜は使わない）、1手16シミュレーション、どの条件も合計1000万局。16ブロックの Bottlenecked ResNet（128チャネル）、AdamW、学習率 0.001。千日手の棋譜は学習から除いた。
- 比べた環境：通常の初期局面だけ（Base）、将棋81万だけ、将棋81万で事前学習してから通常の初期局面、など5つ。
- 結果：水匠5（1000ノード）を ±0 として、Base は +214 Elo。将棋81万で事前学習すると、居飛車で約 +30、振り飛車・相振飛車で約 +50 Elo 上がった。
- 但し書き：「今回作成したプレイヤ側も水匠側も最高パフォーマンスの設定にはなっていない」。他のプログラムとの強さの比較ではなく、環境どうしの比較が目的のため。

相手をノード数で固定するのは、勝率が測れる強さにするためと、計算機によらず再現できるため。将棋の論文で相手と条件を同じにしたのは、AlphaZero 対 Elmo（同じ時間、AlphaZero が同等以上に強い）と MuZero 対 AlphaZero（同じシミュレーション数）だけだった（原文で確認）。

初期局面から始めないのは、両者とも決定的に指すため（同じ2局を繰り返すだけになる）。Science 版の AlphaZero も、将棋で人間の序盤の局面から始めた対局をしている。

| 500ノード | 6勝84敗 | 7勝83敗 | 1勝89敗 | 4勝86敗 |

1. **局面の集まりが違う。** 全局面の57%は相手のライオンを取れる局面で、ほかにも対局では現れない局面が多い。対局で現れる局面に近い 4,222局面では 6T が最下位で、総当たりと同じ傾向。→ 対局に出た局面だけで一致率を測れば確かめられる。
2. **測っているものが違う。** 一致率は探索なしの policy の1手だけ。対局は1手64シミュレーションの探索をするので、value の良さも効く。6T は policy は良いが value が悪い、という可能性。→ 全局面で value の符号の正答率（中屋敷・金子と同じ測り方）を出せば確かめられる。
3. **差が小さい。** 総当たりの差は全体で約70 Elo。信頼区間で見ると、6T が確かに下なのは 5R1T・TRRRRT に対してだけ。

### B. 9×9：外部の相手には 10R が上なのに、直接対局では R3(RRT) が上

|---|---|---|---|

| AobaZero w50 の得点率（試し、各90局） | 16回／64回 | 53%／63% | 44%／62% |

| 直接対局（R3(RRT) の得点率） | 1手2秒、Gumbel ノイズあり、初期局面から、400局 | — | 60.6%（55.8〜65.4%） |
| 直接対局（R3(RRT) の得点率） | 16回／64回、ノイズなし、人間の開始局面、各90局 | — | 40.0%／48.3% |

ポイント：直接対局でも、16・64回（人間の開始局面）では R3(RRT) は上回っていない。R3(RRT) が上回ったのは「1手2秒・ノイズあり・初期局面から」の対局だけ。つまり食い違いは「外部か直接か」ではなく、条件の違いから来ている可能性が高い。

考えられる理由（どれも確かめていない仮説）：
1. **探索の量。** 1手2秒は16・64回よりずっと多く探索する（回数は測っていない）。探索が少ないと policy の1手目の良さが効き、多いと value の良さが効く。10R は policy、R3(RRT) は value が良い、という可能性。
2. **開始局面。** 初期局面からの対局は自己対局で見慣れた局面。人間の棋譜の局面は見慣れない局面で、R3(RRT) の方がそこで弱い可能性。
3. **ノイズ。** 2秒の対局は Gumbel ノイズあり。
4. **局数。** 90局の比較は信頼区間が ±10ポイントあり、差を言えない。本番（各400局）を待つ。

切り分けるなら（どれも費用は未確認）：直接対局を、(a) 64回・初期局面から・ノイズあり、(b) 800回・人間の開始局面・ノイズなし、で行えば、探索の量と開始局面のどちらが効いているかがわかる。

**持ち駒の寄与についての注意（10月21日にわかったこと）**
- 駒打ちの手について、打つ駒の入力を 0 にするとその駒は打てなくなるため、その手の確率の下がり方は、もとの確率とほぼ同じになる（局面129903344：確率 0.850、下がり方 0.845。局面145618616：0.006 と 0.006。9×9 の S\*8b：0.449 と 0.437）。つまり、打つ駒の policy への寄与は、その手の確率以上の情報を持たない。前に「キリンを消すと G\*c3 の確率が 0.845 下がる（持ち駒を使っている）」と書いたのは、確率を言い直しただけだった。論文の本文は直した。
- 動物将棋の2局面は value が勝ちでほぼ確定（0.997、0.999）で、持ち駒を消しても value は 0.01 以下しか変わらない。
- 意味があるのは value への寄与と、駒打ちでない手への寄与。9×9 の S\*8b の局面では、相手の持ち駒（金 −0.324、銀 −0.273、桂 −0.127）が value を下げていることが読み取れる。
- 動物将棋の持ち駒の図は、value が確定していない局面や、駒打ちでない手への持ち駒の寄与が大きい局面を選び直す必要がある（論文に【未定】として残した）。

## 4. 持ち駒の可視化

2つのゲームで同じ方法にした（案 (b) と (c)）。駒打ちの局面で、打つ先のマスを起点にした Attention Map と、持ち駒の寄与（手番側・相手の持ち駒の入力を1種類ずつ 0 にしたときの value と、その駒打ちの手の policy（確率）の下がり方）を並べる。持っていない駒の寄与は 0 になることを確かめた。例：E*a2 が最善手の局面で、手番側のゾウを 0 にすると E*a2 の確率が 0.51 下がった（6T）。

試作の案の一覧（10月18日に決めたもの）：

持ち駒はマスを持たず、全マスの入力に同じ値として入るので、Attention Map に持ち駒の場所はない。

| 案 | 内容 |
|---|---|
| (a) | 持ち駒を1枚減らした入力との、Attention の差を盤に描く |
| (b) | 最善手が駒打ちの局面で、打つ先のマスを起点にした Attention Map |
| (c) | 持ち駒の入力を消したときの、勝ちやすさと指す手の確率の変化 |
| (d) | 持ち駒の入力への勾配による寄与 |
| (e) | 持ち駒の種類ごとに、どのマスに打ちたいか（方策の駒打ちの確率）を盤に描く |
| (f) | 持ち駒を1枚増やした入力との、Attention の差 |
| (g) | 盤の横に駒台を描き、(c)・(d) の値で持ち駒に色を付けた図 |

### 持ち駒の可視化の決定（10月21日）

論文に入れるのは (a)(b)(c)(e)。(d)(f)(g) は入れない。

- **(c) を「消す」から「相手に1枚渡す」に変えた。** 持ち駒の平面を 0 にすると駒の総数が 7 枚になり、実際には起きない局面になる。1枚を相手の持ち駒に移せば総数は 8 枚のままで、完全解析で勝敗を引ける。
- **打つ駒の駒打ちの手の policy の棒は出さない。** 打つ駒を渡すとその手は打てなくなり、下がり方がもとの確率とほぼ同じになるだけ（情報がない）。
- **動物将棋の value は先手から見た値**（盤を回さないため）。後手番では符号を反転して手番側にそろえた（反転を忘れると、value の変化が勝敗と合わないように見える）。9×9 の value は手番側から見た値。
- **完全解析で確かめた**：無作為な局面（先手番・後手番の向き各 20,000）のうち手番側が持ち駒を持つ局面で、1枚を渡した局面を作り、完全解析にある 6,882 組で比べた。渡すと勝敗が悪くなる 1,495 組で value が下がった割合は 6T 99.6%、RRTRRT 99.3%、6R 98.9%、5R1T 99.5%（下がり方の中央値 約 1.0）。勝敗が変わらない組の |value の変化| の中央値は 0.06〜0.11。
- **(a) の大きさ**（局面129903344、G\*c3、起点 c3、キリンを渡す）：6T 第5ブロック H4 は b1 +0.58／b2 −1.21、第4ブロック H1 は b1 +0.46／a3 −0.78。ほかの 22 ヘッドは 0.15 以下、RRTRRT は全ヘッド 0.01 以下。
- **(c) の例**（局面146387506、先手番、キリンとゾウを持つ。キリンを渡すと完全解析で勝ち→負け）：6T は唯一の最善手 c1c2。value はキリンを渡すと 1.83、ゾウで 1.72 下がる。RRTRRT は b1c2（最善でない）、1.60・1.51。
- **9×9 の問題の局面は直前の手順がない入力だった**（tsume_shogi.py の sfen_to_tensor は前の 7 局面を 0 にする。学習中の対局では 8 手目以降は必ず埋まっている）。ResTNet の論文は入力の作り方を書いていないが、MiniZero の囲碁も直近 8 手を重ねる（Hex は今の局面だけ）。ResTNet の可視化の局面はすべて実際の対局から取っている。
- **藤井－羽生は棋譜から前の 7 局面を入れた**（10月21日）。棋譜：https://sakidori-ch.com/fujiisouta-20180217 （出典：連盟モバイル、119手）。86手目「8九飛成」は指せないので 8九歩成、115手目「5五銀」は 5五銀打と読んだ。こう読むと、合法に最後まで並ぶ読み方は1通りで、60・80・118手目の局面がプリセットの SFEN と盤・手番・持ち駒・手数まで一致した（cshogi で確認）。手順は tsume_shogi.py の FUJII_HABU_2018。プリセットの SFEN を渡すと、C++ の環境（学習と同じ getFeatures）で初手から並べた入力になる。
- **SFEN からの入力は千日手の平面も違っていた。** C++ の環境は初めて出た局面でも「千日手 1 回」の平面（28番）を全マス 1 にするが、sfen_to_tensor は 0 だった。1 に直した（効果は小さい：80手目の ▲5五銀 20位→11位）。
