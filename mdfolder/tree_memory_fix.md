# MCTS木プールのメモリ削減（actor_mcts_tree_max_children）

（2026-07-20。800シミュレーション化で自己対戦ワーカーがOOM Killされた問題の修正記録）

## 問題

minizeroは並列ゲームごとにMCTSノードプールを事前確保する:

```
tree_node_size = (actor_num_simulation + 1) × 全行動数   # actor_group.cpp
```

将棋は行動数11,259のため、800シミュレーション×256並列で約200GBを要求し、
ホストRAM(128GB)を超えてOOM Killerに殺された（64シミュレーション時代は
約17GBで偶然収まっていた）。

## 根拠（なぜ削減しても安全か）

- ノード確保は展開(expand)時のみで、確保数は**その局面の合法手数**
  （全行動数ではない）。1探索の消費上限 = (シミュレーション数+1) × 局面あたり合法手数
- 将棋の1局面の合法手の既知最大値は**593手**（人工局面）。通常は80〜150手
- よってプールは (sims+1) × 全行動数(11,259) ではなく (sims+1) × 上限値で足りる
- 探索・学習の挙動は完全に不変（予約量が減るだけ）。AZ論文はメモリ管理を
  規定しておらず、論文準拠性とは無関係

## 実装

1. **`actor_mcts_tree_max_children`**（新設定、デフォルト0=従来動作=全行動数）
   - `configuration.{h,cpp}`
   - `actor_group.cpp::createActors()`: プールサイズ計算で 0以外ならこの値を使用
2. **プール溢れのランタイムガード** — `tree.h::allocateNodes()`
   - 従来は `assert` のみで、リリースビルド(NDEBUG)では消えて無言のメモリ破壊になる
   - 常時有効のチェックに変更: 超過時はエラーメッセージ
     （使用量と設定名を表示）を出して即 `abort`
3. **将棋cfg**: `actor_mcts_tree_max_children=1024`
   - 既知最大593の約1.7倍のヘッドルーム。万一超える局面が存在しても
     ガードが即検知するので、値を上げて再実行すればよい

## 効果（800シミュレーション時の自己対戦ワーカー）

| | プール/ゲーム | 256並列 |
|---|---|---|
| 修正前（0 = 11,259） | ~0.87 GB | ~200 GB (OOM) |
| 修正後（1024） | ~79 MB | ~20 GB |

## 注意

- 将棋以外のゲームはデフォルト0のまま（行動数が小さく元々問題ない）
- `[Tree::allocateNodes] node pool exhausted` が出た場合は
  cfgの `actor_mcts_tree_max_children` を上げる
