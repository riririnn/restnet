## 2. Attention Map とは何か

```
Q = W_q · x        # Query: 「何を探しているか」
K = W_k · x        # Key:   「何を持っているか」
V = W_v · x        # Value: 「実際に渡す情報」

attention_logit[i,j]  = (Q[i] · K[j]) * scaling + relative_bias[i,j]
attention_weight[i,j] = softmax_j(attention_logit[i,:])
output[i] = Σ_j attention_weight[i,j] * V[j]
```

`attention_weight[i,j]` を可視化している。
**「どの手を指すか」とは直接関係しない**。「マスiの表現を作るためにマスjをどれだけ参照したか」。

## 3. なぜ均等分散になるか（原因4つ）

### 原因A：訓練ステップ不足
AlphaZero学習の初期は方策・価値の学習が優先され、Q・K射影とrelative_biasの勾配は小さい。
→ iterが進めば改善する可能性。

### 原因B：Residual接続によるバイパス（"Lazy Attention"）
`output = x + MSA(LN(x))` の残差xが支配的なため、Attentionが均等（≈mean(V)）でも
損失は下がり、Attentionに学習圧力がかからない。

### 原因C：将棋タスクに空間集中Attentionが不要な可能性
Conv（R-block）が局所パターンを既に捉えており、T-blockは「大局の均等集約」で十分かもしれない。
この場合、均等分散はバグではなく設計通りの動作。均等分散のAttentionは
Global Average Poolingとして機能する（`output[i] ≈ mean(V)`）。

### 原因D：Softmaxの温度が高い
`scaling = 1/sqrt(d_head) = 0.125`（emb 256 / 4ヘッド → d_head=64）。
標準値だが、訓練済みモデルでは事後変更不可。


## 5. 実装済み可視化の仕組み

### Pre-softmax logit（xai_analysis.py `get_pre_softmax_data`）
モデルコードを変更せず、各Tブロックの `attend`（nn.Softmax）にフォワードフックを仕掛け、
softmax前の `dots`（Q・K内積+relative_bias）を横取りする。
値域 ±0.3 程度で、softmax後（幅0.008）の約60倍の情報量。

### Relative Position Bias（xai_analysis.py `get_relative_bias_maps`）
`relative_bias_table` パラメータを直接読み、`relative_index` で (N,N) に展開。
クエリ位置を指定して9×9盤面に表示（赤=正バイアス、青=負バイアス）。
学習前はほぼ全面白（ゼロ付近）。

**わからないこと**：1 つのヘッド、1 回の学習。局面は完全解析から一様に選んだもので、対局で現れる局面ではない。ヘッドが局面の正解に沿うのか、モデル自身の手に沿うのかは、ここでは分けていない（policy が最善手を選ばないと 32〜37% に下がる。局面の数は少ない）。取られないマスの中での一致も、同じ理由で、粘る手を見ているためとは言えない。重みが手の選択に使われているかは、この数え方ではわからない。

### R を含む構成で query と key の重みが weight decay の大きさのままなのはなぜか

**測ったもの**：ヘッドごとに query と key の重みをまとめて、次の 3 つを weight decay と比べる（どれも 1 より小さければ weight decay が勝つ）。比は学習率と momentum によらない。

- 1 バッチの比：1,000 局面の損失の勾配のノルム ÷（0.0001 × 重みのノルム）。
- 一貫した部分の比：8 バッチの勾配の、違うバッチどうしの内積の平均の平方根 ÷（同じ分母）。バッチごとのばらつきを除いた、毎回同じ向きの部分。
- 増える強さ：query の重みの転置 × key の重みという積についての勾配の最大特異値 ÷ 0.0001（前半 4 バッチの特異ベクトルを、後半 4 バッチに当てた値）。query の勾配は key の重みに比例するので、両方が小さいときはこの値が 1 を超えないと増えない（一次の近似。勾配との関係は数値でも一致、相対誤差 1e-15）。

**まず頼まれた測定（論文の重み、40,000 ステップ）**：data/dobutsu_all/moves_100k_seed1.bin の、相手のライオンを取れる局面とトライ済みの局面を除いた入力から 1,000 局面 × 8。損失は policy（最善手に等しく分けた交差エントロピー）と value（完全解析の結果との二乗誤差）の和。BatchNorm は保存された統計（学習時の統計にすると、この局面では RRTRRT の value の符号の一致が 0.836 から 0.599 に下がり、測定にならない）。

| 論文の重み | 1 バッチの比 | 一貫した部分の比 | 増える強さ |
|---|---|---|---|
| RRTRRT 第 3 ブロック | 0.89〜0.98 | 0.29〜0.40 | 3.0〜6.0 |
| RRTRRT 第 6 ブロック | 1.25〜2.13 | 0.68〜1.03 | 8.2〜11.5 |
| 6T の 24 ヘッド | 7.2〜465 | 4.8〜333 | 35〜1,949 |

**この測定はきれいでない。これだけでは結論を出せない。** 学習の損失は、自己対局の局面と探索の分布・対局の結果に対するもの。無作為な局面と完全解析の答えは、モデルが学習していない問題である（policy の損失 1.58、value の損失 0.50）。論文の重みの自己対局の棋譜は、ここにない。わかるのは、同じ局面で RRTRRT の勾配が 6T より大幅に小さいことだけ。

**学習率などの設定が同じ学習の棋譜で測った**（models/dobutsu/v2。環境は作り直したもので、入力は 19 平面、論文の重みは 20 平面。学習率は v2 の記録で 0.02 のまま。40,000 ステップで RRTRRT の query-key の大きさは 0.0043〜0.0046 で、論文の重みと同じ）：その時点の学習に使われた直前 20 iteration の棋譜から 8,000 局面を一様に取り、棋譜の探索の分布と対局の結果で、学習と同じ損失（BatchNorm もバッチの統計）で測る。学習の記録に近い：40,000 ステップの RRTRRT で value の損失 0.120（記録 0.127〜0.131）、policy の一致 0.924（0.921〜0.922）、policy の KL 0.114（0.117〜0.120）。

| v2 の学習 | 2,000 ステップ | 10,000 ステップ | 40,000 ステップ |
|---|---|---|---|
| RRTRRT 1 バッチの比 | 2.9〜4.9 | 1.8〜2.7 | 0.26〜0.38 |
| RRTRRT 一貫した部分の比 | 0.76〜0.88 | 0.31〜0.44 | 0.03〜0.09 |
| RRTRRT 増える強さ | 1.2〜4.4 | 1.0〜2.5 | 0.12〜0.54 |

- RRTRRT の最初と 40,000 ステップの重みの cos は query と key で 0.9999〜1.0000、大きさは 0.4494 倍（weight decay だけの予測 exp(−0.8) = 0.4493）。value の重みは cos 0.96、0.47 倍で、動いている。
- 同じ T ブロックの value、出力、MLP の重みの 1 バッチの比は 37〜68（40,000 ステップ）。勾配はブロックには届いている。query と key にだけ小さい。

**わかること**（v2 の RRTRRT）：query と key では、毎回同じ向きの勾配が測った 3 つの時点で weight decay より小さく、重みは最初の向きのまま縮んだ。「weight decay の大きさのまま」は、勾配が weight decay に負けているため、で説明がつく。6T は同じ時点で勾配が大幅に大きい。

**わからないこと**：なぜ R があると query と key の勾配が小さいのかは、確かめていない（R ブロックが仕事を受け持つから、という説明は仮説で、介入の実験はしていない）。増える強さは 2,000 ステップで 1 を少し超えるのに大きさが増えなかった理由も、確かめていない（勾配の向きが学習中に変わるためかもしれない）。2,000 ステップより前は測っていない。論文の重みそのものの学習の勾配は測れない。各構成 1 回の学習。

結果：data/dobutsu_all/qk_gradient.csv と .txt（論文の重み。4,000 ステップの途中の重みも含む）、qk_gradient_v2_selfplay.csv と .txt（v2）。
