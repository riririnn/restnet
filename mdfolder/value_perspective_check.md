# value が学習しない問題の検証（2026-08-25）

事前学習で **policy は学習できたが value が全く学習しない**。その原因を切り分けるための検証手順。
専門用語には初出時に説明を入れる。

## 1. 前提となる用語

### policy と value

ネットワークは局面を入力として、2つの出力を出す。

| 出力 | 意味 | 教師データ |
|---|---|---|
| **policy**（方策） | 次にどの手を指すべきかの確率分布 | 棋譜で実際に指された手 |
| **value**（価値） | この局面はどちらが勝ちそうかの数値 | その対局の最終的な勝敗 |

value は `-1`（後手勝ち）〜 `+1`（先手勝ち）の範囲を取る。
将棋AIは探索（MCTS）の途中でこの value を使って「この枝は有望か」を判断するので、
**value が機能しないと探索が局面の良し悪しを区別できなくなる**。

### step（ステップ）と epoch（エポック）

- **step**: データを一定数まとめた「バッチ」1つ分で、ネットワークの重みを1回更新すること
- **epoch**: 手持ちのデータ全体を1周すること

今回は 644万局面を 1024 個ずつのバッチで学習したので、1 epoch = 約 6,300 step。

### loss（損失）

正解からどれだけ外れているかの数値。**小さいほど良い**。学習とは loss を下げる作業のこと。

value の loss は **MSE（平均二乗誤差）** で測る。予測と正解の差を2乗して平均したもの。

```
正解が +1、予測が +1   → 誤差 0     （完璧）
正解が +1、予測が  0   → 誤差 1     （何も分かっていない）
正解が +1、予測が -1   → 誤差 4     （正反対）
```

### 「loss_value ≈ 1.0」が意味すること

教師データは `+1` か `-1` のどちらかで、その割合はほぼ半々（先手勝ち50.9% / 後手勝ち48.7%）。

このとき **常に 0 を出力する**と、誤差は毎回 1 になり、平均も 1.0 になる。

```
loss_value = 0.997  →  ネットワークは全局面で「引き分け(0)」と答えている
                       = 勝敗について何も学べていない
```

実測では 130,000 step 回しても 0.997 のまま動かなかった。

### 過学習（overfitting）

学習に使ったデータは正解できるが、**見たことのないデータには通用しない**状態。丸暗記のこと。

これを検知するため、データの一部（3,000局）を学習に使わず取っておき（**検証データ / test**）、
そちらの成績も測っている。

```
学習データの精度 57.0%  /  検証データの精度 48.9%   ← 差が開くほど暗記寄り
```

## 2. 何が起きているか

policy は順調に学習した。value だけが全く動かない。

| | step 5,000 | step 130,600 |
|---|---|---|
| accuracy_policy（学習） | 39.5% | 57.0% |
| accuracy_policy（検証） | 38.3% | 48.9% |
| **loss_value** | **0.9975** | **0.9975** |

データ量・step 数・学習率のどれを変えても動かなかったので、**量の問題ではない**。

### 決定的な手がかり

以前の診断で、**50局だけに絞ると value は学習できた**（loss_value 0.995 → 0.089）。

```
    50局 → 学習できる
68,203局 → 学習できない
```

普通は逆で、データが多いほど学習しやすい。この逆転は
「**暗記はできるが、汎化できる規則が存在しない**」ことを示す。

50局なら「この局面はこの結果」と丸暗記できるが、68,203局では暗記しきれず、
かといって一般化できる法則も見つからない、という状態。

## 3. 疑っている原因：教師信号の「視点」

### 手番相対とは

将棋は先手と後手で盤の向きが逆になる。そこで多くの将棋AIは、
**常に自分が手前に来るように盤を回転させて**ネットワークに入力する。これを手番相対という。

```
先手番の局面 → そのまま入力
後手番の局面 → 盤を180度回転して入力（自分が手前に来る）
```

こうすると「自分の歩が前に進む」という関係が先後で共通になり、学習しやすくなる。
実際 `shogi.cpp` の `getFeatures()` はこの処理をしている。

```cpp
bool is_white_turn = (turn_ == Player::kPlayer2);
if (is_white_turn) { r = 8 - r; f = 8 - f; }   // 後手番なら盤を回転
```

### 食い違い

ところが **value の正解ラベルは回転させていない**。常に「先手が勝ったか」で与えている。

```cpp
data.value_ = env_loader.getReturn();   // 常に先手視点（+1=先手勝ち）
```

すると、こうなる。

```
局面A: 先手番、自分（先手）が優勢    → 入力は「手前が優勢」  正解 +1
局面B: 後手番、自分（後手）が優勢    → 入力は「手前が優勢」  正解 -1
```

**入力の見た目が同じなのに、正解が正反対になる。**

ネットワークから見ると、同じ入力に +1 と -1 の両方の正解が与えられている状態に近い。
その場合の最適な答えは「両者の平均 = 0」であり、まさに観測された挙動と一致する。

### 「先手固定」の何が悪いのか

同じ見た目の入力に、正反対の正解が混ざるのが問題。ネットワークは入力から正解を予測する装置なので、
**同じ入力に +1 と -1 が半々で与えられると、最も損の少ない答えは「その平均 = 0」になる**。

損失は誤差の2乗で測るため、+1 と -1 の両方に対して損を最小化する点はちょうど中間の 0 になる。
これは学習が失敗しているのではなく、**与えられた条件下での最適解が 0 だという状態**。

観測された「常に 0 を出力し、loss_value が 1.0 から動かない」挙動と一致する。

### 本来どう設定されるべきか

**入力と正解の視点を揃える。** 入力が「手番側から見た盤面」なら、正解も「手番側から見た勝敗」にする。

```
先手番、自分が勝った局面 → +1
後手番、自分が勝った局面 → +1   ← 先手固定だと -1 になってしまう
```

こうすれば「手前が優勢な盤面 → +1」という一貫した対応になり、素直に学習できる。
AlphaZero 系の実装では通常こちらを採る。

### 自己対局ではどう設定されているか

**同じ「先手固定」を使っている。** 教師あり学習だけの特殊な設定ではない。

```cpp
// minizero/minizero/environment/shogi/shogi.cpp
float ShogiEnv::getEvalScore(bool is_resign) const {
    return (winner_ == GameResult::BLACK_WON) ? 1.0f
         : (winner_ == GameResult::WHITE_WON) ? -1.0f : 0.0f;
}
```

自己対局では対局終了時にこの値が `RE` タグに書かれ（`base_env.h:211`）、
学習時に `getValue(pos)` がそれを全局面に返す（`data_loader.cpp:172`）。
囲碁・オセロも同じ書き方（`go.h:131`、`othello.h:77`）。

**ところが自己対局では value が学習できている。** これは仮説にとって不都合な事実なので、
数値で確認しておく。

| | 人間棋譜（今回） | 自己対局（restnet64_v2） |
|---|---|---|
| 勝敗分布 | 先手50.9% / 後手48.7% / 引分0.4% | 先手56.6% / 後手22.9% / 引分20.5% |
| 何も学ばない場合の loss_value | 0.996 | 0.681 |
| 実測の loss_value | **0.9975**（下限と同じ） | **0.530**（下限を下回る） |
| 判定 | 学習ゼロ | 学習している |

「何も学ばない場合の loss_value」とは、局面を一切見ずに**常に同じ値（勝敗の平均）を答えた**ときの誤差。
この値を下回っていれば、局面ごとの違いを捉えていることになる。

自己対局は 0.681 に対し 0.530 なので、**局面を見て判断できている**。
一方こちらは 0.996 に対し 0.9975 で、**下限すら下回っていない**。

### したがって「視点だけが原因」とは断定できない

同じ規約で自己対局が学習できている以上、視点の不一致だけでは説明がつかない。
考えられる差は次の通り。

- **勝敗の偏り**: 自己対局は先手56.6%と偏っており、「先手有利」を覚えるだけでも損失が下がる。
  人間棋譜は50.9%対48.7%でほぼ均衡しており、そうした近道が無い。
- **対局の質**: 自己対局は平均284手でエンジン同士の一貫した指し手。
  人間棋譜は平均94手で、レート1800帯の互角の勝負は結果の揺らぎが大きい。
- **視点の不一致**: 学習を難しくする要因ではあるが、致命的とは限らない。

つまり視点は**複数ある候補の1つ**。だから実験で確かめる。

### ただし情報自体は与えられている

入力の中には「今どちらの手番か」を示す平面（channel 360）が含まれている。

```cpp
float turn_val = (turn_ == Player::kPlayer1) ? 1.0f : 0.0f;   // 先手番なら1.0
```

なのでネットワークは原理的には
「手番平面が 0 なら符号を反転する」というルールを学べば正解できる。**学習不可能ではない。**

しかしこれは掛け算的な条件分岐で、足し算の積み重ねが得意なニューラルネットには難しい部類に入る。
さらに value 出力の直前で `AdaptiveAvgPool2d` により盤面全体が1本のベクトルに潰されるため、
条件分岐に必要な情報が薄まる。

policy が順調なのに value だけ止まっているのは、この仮説と整合する。
policy は手番相対のまま素直に学べるが、value だけが余計な条件分岐を要求されている。

## 4. 検証方法

**value の正解ラベルを手番視点に変える。** 変更は1行。

```cpp
// 変更前：常に先手視点
data.value_ = env_loader.getReturn();

// 変更後：手番から見た勝敗（後手番なら符号を反転）
data.value_ = env_loader.getReturn() * (p.second % 2 == 0 ? 1 : -1);
```

`p.second` はその局面が何手目か。将棋は先手から始まるので、
偶数手目 = 先手番、奇数手目 = 後手番になる。

これで入力と正解の向きが揃う。

```
局面A: 先手番、自分が優勢 → 入力「手前が優勢」 正解 +1
局面B: 後手番、自分が優勢 → 入力「手前が優勢」 正解 +1   ← 揃った
```

### 手順

```bash
# 1. C++ を変更してビルド
scripts/build.sh shogi release

# 2. 別ディレクトリでゼロから学習（既存の結果を壊さない）
tools/quick-run.sh pretrain shogi train shogi_9x9_valuetest 10000
```

10,000 step で約1時間。既存の `shogi_9x9_human` とは別のディレクトリに出力するので、
これまでの学習結果は残る。

### 判定基準

比較対象は同じ 10,000 step 時点の既存結果（`loss_value ≈ 0.997`）。

| 結果 | 意味 | 次の行動 |
|---|---|---|
| `loss_value` が 0.9 以下に下がる | **視点の不一致が主因と確定** | この方式で本学習をやり直す |
| 0.99 台のまま | 視点は主因ではない | 残る候補（勝敗が均衡しすぎている、人間棋譜の結果が本質的に予測しにくい）を調べる |

判定の目安に 0.9 を使うのは、**何も学ばない場合の下限が 0.996** だから。
これを明確に下回れば、局面ごとの違いを捉え始めたと言える。

自己対局が 0.681 の下限に対して 0.530 まで下げている（約22%改善）ことを考えると、
視点が主因なら同程度の改善が見えるはず。

policy 側（`accuracy_policy`）は変更の影響を受けないはずなので、
そちらが従来通り伸びていれば、変更が他を壊していないことの確認になる。

## 5. この変更の位置づけ

minizero は囲碁・オセロなど他のゲームでも「常に先手視点」の規約を採っている
（`go.h:131`、`othello.h:77` も同じ書き方）。**今回の変更はこの規約から外れる。**

論文の 19×19 囲碁は同じ規約で教師あり学習に成功しているように見えるが、
その学習コードは公開状態のままでは実行できず（詳細は `bootstrap_pretraining.md`）、
実際にどの設定で動かしたかは確認できない。

したがって現時点では、

- 規約自体が誤っている
- 教師あり学習という条件でのみ問題が顕在化する
- 将棋固有の事情がある

のいずれかを断定できない。**まず事実を確かめる**のがこの検証の目的。

結果が出れば、それ自体が報告に値する知見になる。
