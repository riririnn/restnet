## 1. 発見したバグと修正（C++/minizero）

| 問題 | 原因 | 修正 |
|---|---|---|
| 温度が学習序盤から0.25に固定 | 減衰式が `iteration/zero_end_iteration` で、チャンク実行(CHUNK=1)では常に進捗≈1.0 | 減衰OFF、全手τ=1（AZ準拠）。`_move_cutoff` パラメータも新設（現在0=未使用、30でAGZ方式） |
| 長期戦が最適戦略化 | 上限到達時の27点法判定が「駒得維持で+1」を与え、詰みと同価値 | **上限到達=引き分け(z=0)** に変更（AZ準拠）。27点法コード削除 |
| 白が引き分けを歓迎 | コンテンプト(-0.2)が黒視点固定 → MCTSの符号反転で白には+0.2 | コンテンプト削除、引き分け=0（AZ準拠） |
| 割引率0.99 | 木のバックアップで深さ毎に0.99倍するだけで学習ターゲットに無関係、PUCTを歪める | γ=1（AZ準拠） |
| 千日手の過剰検出 | ハッシュが手番を含まない(getNoTurnHash) | getHash（手番込み）に変更 |
| 連続王手の見逃し/誤検出 | 直前手番側しか検査しない・反復局面自体を検査から除外 | 反復区間の全局面を両側について検査する実装に書き直し |
| 相入玉が必ず上限引き分け | 27点法削除の副作用（詰み不可能な局面クラス） | **入玉宣言法**(CSA 27点)を実装。`env_shogi_enable_declaration_win`(デフォルトtrue) → [entering_king_rule.md](entering_king_rule.md) |
| 自己対戦ワーカーがOOM Kill | 木プールを (sims+1)×全行動数11259 で事前確保。800simsで~200GB | `actor_mcts_tree_max_children=1024` で確保量を合法手上限ベースに。assertを常時ランタイムガード化 → [tree_memory_fix.md](tree_memory_fix.md) |

## 2. 追加した仕組み

- **終局理由のSGF記録**: `RR[...]` タグ（mate/resign/stalemate/perpetual_check/
  sennichite/declaration/cap）。`sgf_stats.sh` は宣言列を分離して集計、
  旧SGFは手数ヒューリスティックにフォールバック
- **LRスケジュール**: curriculum_train.sh がAZ論文の3段減衰(1/7・3/7・5/7地点で
  1/10)を `-conf_str` で毎チャンク適用。初期値 `LR_BASE` はバッチ比換算
  (0.2×batch/4096; batch1536→0.075) → [hyperparameters.md](hyperparameters.md)
- **カリキュラム廃止**: 上限は512固定（AZ論文値。手数チャネルの/512正規化とも整合）。
  CAPS=(512)、複数値に戻せば再有効化可能

## 3. 主要な判断と根拠

- **Gumbel維持**（AZの素PUCTに戻さない）: AZより新しい改善手法であり、
  従来ResTNet実験(gaz)との一貫性を優先
- **バッチ1536維持**（AZの4096に揃えない）: Tブロックの学習安定性は
  ResTNet領域。等価性はLR側のスケーリングで確保
- **シミュレーション数 800→64**: 800はAZ論文値だが1GPUでは~6000
  1080Ti-GPU時間（ResTNet論文: 囲碁9路64simsで200時間）となり1週間制約で不可能。
  ResTNet論文と同じ64+sample16に回帰。
  旧n64実測で詰み・投了14-39%が出ていたため「64では詰み0」は誤りで、
  旧失敗の主因は報酬構造（修正済み）だった可能性が高い
- **判定基準（事前固定）**: iteration 20で sgf_stats の詰み・投了率が
  上昇トレンドになければ「64は探索律速」と結論し増やす

## 4. 性能チューニングの知見（RTX PRO 6000 / 24コア / 128GB）

- 自己対戦は**CPUフェーズ⇄GPUフェーズの交互実行**（actor_group.cpp）。
  GPU使用率=フェーズ時間比であり、**1プロセスの設定値では上限を超えられない**
- 実測: 256並列/8スレッド=42%が単プロセス最良。512並列は木のワーキングセット
  (40GB)でCPUフェーズがDRAM待ちになり悪化。スレッド増(20)も競合で悪化
- **GPUを埋める正解はワーカープロセス追加**（zero-worker.sh で同一サーバーに
  sp参加）。800sims時代: 2本で50-65%。64sims: 木が浅くCPUフェーズが軽い
  ため**2本で70%**に到達。sp合計3本が上限（コア数）
- 運用の詳細（tmux方式・止め方・再学習手順）→ [docker_container_usage.md](docker_container_usage.md)

## 5. Git/サブモジュール運用

- minizero はフォーク(riririnn/minizero)の `shogi` ブランチ。
  クローン後は `git submodule sync` 必須（mainの.gitmodulesは本家指し）
- コミット順: minizeroでコミット→push→親で `git add minizero`→push。
  サブモジュールpush忘れは他マシンで参照解決エラー
- configs/ 配下の .cfg は追跡対象（.gitignoreに `!configs/**/*.cfg` 例外）
- 継続ランは**ランディレクトリ内cfgが優先**。設定変更時はラン作り直しが安全
